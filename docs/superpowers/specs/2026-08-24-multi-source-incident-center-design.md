# 多源生产事故中心设计

## 状态

已确认，待实施计划。本文描述目标架构，不代表仓库已经实现。

## 项目决策

本项目在 `/Users/shaoqian.li/Documents/incident-intelligence` 以独立 Git 仓库从零初始化。它只建设多源告警归集、事故关联、自动取证、AI 分析和事故运营能力。

故障注入是另一个独立平台。两个项目具有独立源码、Git 历史、数据库、Secret、镜像、部署包、ServiceAccount 和 UI。它们不共享代码模块、不读取对方数据库，也不通过运行时隐藏菜单伪装成同一产品。

## 理想业务效果

平台从 Prometheus、APM、日志告警、Kubernetes、SLO、变更系统和人工报告等来源接收运行事件。每个事件先成为不可变 SignalEvent，同一条件的更新和恢复被去重为 Alert。只有需要人工动作或满足影响条件的 Alert 才进入关联引擎。关联引擎结合实体、时间、服务拓扑、症状和变更创建或更新 Incident。

事故创建后，DiagnosisRun 组合通用基础诊断与专用增强包，执行版本化预定义只读查询，生成“查了什么、结果是什么、意味着什么”的确定性结果并封存证据快照。AI 只分析快照，输出必须引用真实证据并通过事实一致性校验。操作员在同一事故工作台认领、调查、缓解、观察恢复、解决和关闭事故。

## 多源接入

首批只实现 Alertmanager、CloudEvents HTTP 和人工报告三个入口。外部生产者可以保留原协议，由受控 Adapter 转换成统一 SignalEvent。CloudEvents 只作为内部事件信封参考，不要求所有外部系统改造。

SignalEvent 至少包含来源唯一身份、事件类型、发生和接收时间、环境、实体引用、症状族、严重程度、安全摘要、固定属性、来源引用和契约版本。原始无界负载、任意标签、Secret、实验身份和自由 URL 不进入公开接口或 AI 输入。

## 事故关联

首版使用确定性规则，不让 LLM 或黑盒模型自动合并事故。关联顺序包括：

1. 相同稳定关联键；
2. 相同服务、资源或实例；
3. 服务目录一跳依赖；
4. 5–60 分钟范围内的滚动时间窗口，默认 15 分钟；
5. 已审核症状因果或共同根因规则；
6. 同实体邻近部署、配置和 Feature Flag 变更；
7. 经审核发布的人工合并或拆分模式。

高可信规则可以自动加入已有事故。中低可信候选创建独立事故，只提示可能相关。每次关联保存规则版本、使用事实、固定原因码和中文解释。人工合并、拆分和移动告警产生审计反馈，不即时在线改写规则。

## 独立状态机

- Alert：`ACTIVE → RESOLVED` 或 `SUPPRESSED`；
- Incident：`DETECTED → TRIAGING → INVESTIGATING → MITIGATING → MONITORING_RECOVERY → RESOLVED → CLOSED`；
- DiagnosisRun：`QUEUED → COLLECTING → NORMALIZING → SNAPSHOT_READY → ANALYZING → REPORT_READY`，并包含部分、失败和人工复核分支。

恢复事件只更新 Alert。它不能自动关闭 Incident。DiagnosisRun 失败也不能阻断事故认领、缓解和恢复。

## 通用诊断与增强包

诊断计划由四层版本化资产组成：

1. 通用基础包：健康、工作负载、错误、延迟、上下游和近期变更；
2. 实体类型包：Kubernetes、JVM、Node.js、MySQL、外部 HTTP 依赖；
3. 症状增强包：CPU、内存/OOM、延迟/错误率、Pod 重启、数据库连接/锁等待；
4. 受控服务扩展：业务团队通过 Schema、安全审核和回放验证提供的指标及 Runbook 映射。

没有专用增强包时仍执行通用基础包，并明确标记覆盖有限。每项排查必须预先声明查询、参数、超时、容量、脱敏、结果转换、证据角色和失败语义。

## AI 边界

AI 可以综合根因候选、因果链、证据缺口、人工验证和候选缓解建议。AI 不可以访问监控、Kubernetes、事故数据库或故障平台，不可以执行查询、命令或修复，不可以改写事实，也不可以读取故障场景、注入动作和标准答案。

报告必须通过 Schema、证据 ID、告警事实和确定性诊断结论校验。冲突结果进入人工复核，不发布为可信报告。AI 不可用时，页面仍展示确定性取证结果。

## 与故障注入平台的关系

故障平台只负责注入、真实激活、恢复、业务基线和零残留。本项目不知道实验身份。真实监控或通用适配器独立产生事故后，本项目完成盲诊断。报告封存后，故障平台一侧的隔离评测器才能读取标准答案并从本项目公开只读 API 取得报告评分。

一次非生产验收分别输出注入、恢复、检测、关联、取证和 AI 六项结果。“注入成功但无告警”表示实验通过、检测覆盖失败；“证据完整但 AI 错误”表示取证通过、AI 评测失败。

## UI 目标

事故列表以业务影响、主要服务、严重程度、负责人、运营状态、持续时间、关联告警和当前诊断结论为主。详情页依次展示业务影响、当前负责人和下一动作、根因与因果链、支持/反证/缺失证据、统一时间线、诊断版本、恢复检查和关闭清单。内部 ID 和技术详情默认折叠。

## 技术架构

核心控制器、Diagnosis Worker 和 Analysis Worker 统一使用 Python。核心控制器以 FastAPI 提供 HTTP API，使用 Pydantic 定义边界模型；持久化采用 PostgreSQL、SQLAlchemy 和 Alembic。首期异步任务保存在 PostgreSQL，通过租约、心跳与超时接管保证任务可恢复，暂不引入 Kafka。

统一 UI 使用 Vue 3、TypeScript、Vite 和 Pinia。后端以 OpenAPI 作为前后端接口事实来源，前端从契约生成接口类型，避免手工维护重复模型。后端使用 Pytest，前端使用 Vitest，关键端到端旅程使用 Playwright。

前端和核心控制器形成独立构建制品，但默认作为一套平台部署。可选 Worker 使用版本化任务契约注册能力，可独立部署、扩缩容和故障隔离，不与前端直接通信。具体运行时版本、依赖锁定、目录结构和本地启动方式在阶段 1 实施计划中确定。
