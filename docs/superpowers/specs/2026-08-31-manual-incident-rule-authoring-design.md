# 手动 Incident 规则配置设计

## 1. 目的

SignalEvent 负责保存接收事实，Alert 负责表达一次告警生命周期。Incident 识别规则必须只读取 Alert，不能回到 SignalEvent 拼接业务结论，也不能依赖故障注入场景。

本设计先解决“规则如何由人定义、验证和安全发布”，为下一阶段 Incident 候选生成引擎提供稳定输入。规则发布本身不创建 Incident；这样可以先验证规则表达是否清楚、历史命中是否合理，再单独设计候选 Incident 的生成、去重和生命周期。

## 2. 用户流程

### 2.1 规则列表

左侧导航新增“Incident 规则”。页面默认展示真实规则列表；没有规则时只展示空状态和“创建规则”按钮，不创建演示数据。

列表每行集中展示：规则名称、状态、匹配范围摘要、触发条件摘要、最近试运行结果、更新时间。草稿可继续编辑或删除，已发布规则可复制为草稿或停用，已停用规则可查看或复制。

### 2.2 四步创建

界面忠实采用用户选定的第 1 个视觉方案：

1. **基本信息**：名称和用途说明；
2. **匹配范围**：环境、接入源、服务和聚合方式；
3. **触发条件**：观察窗口与结构化条件；
4. **试运行与发布**：选择历史范围、查看命中结果并发布。

页面右侧始终显示中文自然语言摘要，底部提供“上一步”“保存草稿”和下一步操作。保存成功、校验失败和并发冲突必须就地反馈，不能只依赖全局弹窗。

## 3. 规则语义

### 3.1 匹配范围

- `environment`：必选，规则绝不跨环境匹配；
- `alert_source_ids`：可选，空数组表示该环境下所有接入源；
- `services`：可选，空数组表示所有服务；
- `group_by`：只允许 `SERVICE` 或 `ENTITY`。

当 `group_by=SERVICE` 时，缺少 service 的 Alert 不参与计算；当 `group_by=ENTITY` 时使用 Alert 已有的 `entity_key`，不查询 Kubernetes 或其他外部系统补充信息。

### 3.2 时间窗口

`window_minutes` 取值 1 至 60。计算使用 Alert 的平台接收时间：

- 首次进入窗口使用 `first_received_at`；
- 判断活动状态使用 Alert 当前 `state`；
- 历史试运行以每条 Alert 的 `first_received_at` 作为候选窗口终点，向前读取一个观察窗口。

### 3.3 条件

第一版只支持四种条件：

- `DISTINCT_ALERT_NAMES_GTE`：不同 Alertname 数量大于等于整数；
- `ACTIVE_ALERTS_GTE`：活动 Alert 数量大于等于整数；
- `DISTINCT_ENTITIES_GTE`：不同实体数量大于等于整数；
- `MAX_SEVERITY_AT_LEAST`：最高级别至少为 `critical/high/medium/low` 之一。

所有条件使用 AND。每种条件最多出现一次，至少存在一个前三类计数条件；计数阈值取值 1 至 1,000。第一版不提供 OR、嵌套条件、正则、脚本或任意 JSON 编辑。

中文摘要由后端根据结构化规则生成，前端只展示，不自行推导另一套语义。

## 4. 状态与版本

规则状态：

```text
DRAFT ──发布──> PUBLISHED ──停用──> DISABLED
  │                  │                 │
  └──删除            └──复制为草稿────┘
```

- 草稿可修改；已发布和已停用规则不可直接修改；
- 修改草稿会增加 `version`，并令之前的试运行凭证失效；
- 发布要求当前版本存在一次成功且未截断的试运行；
- 修订已发布规则时复制为新的草稿，原规则保持可追溯；
- 所有更新携带期望版本，版本不一致返回冲突，不覆盖较新的修改。

## 5. 历史试运行

试运行只读真实 `alert_lifecycles`：

1. 校验并保存当前草稿；
2. 按环境、来源、服务和最近 1/6/12/24/48 小时筛选 Alert；
3. 按 `group_by` 划分分组；
4. 以 Alert 首次接收时间为时间顺序，计算滚动观察窗口；
5. 对每个窗口执行 AND 条件；
6. 合并同一分组中成员完全相同的连续命中，避免结果重复；
7. 返回命中窗口、分组显示名、总 Alert 数、不同 Alertname 数、不同实体数、最高级别和最多 10 条示例 Alert。

每次最多扫描 10,000 条 Alert，最多返回 100 个命中。超过扫描或返回上限时结果标记 `truncated=true`，允许用户查看，但不能凭该结果发布规则。试运行不创建或修改 Incident、Alert、SignalEvent。

## 6. 后端边界

### 6.1 数据表

新增 `incident_rules`：规则身份、名称、说明、状态、环境、来源过滤、服务过滤、聚合方式、观察窗口、结构化条件、中文摘要、版本、最近成功试运行版本和时间、创建与更新时间。

新增 `incident_rule_dry_runs`：规则 ID、规则版本、历史范围、扫描数量、命中数量、是否截断、结果摘要、执行时间。只保留有界摘要，不复制 Alert 全文。

新增 `incident_rule_operations`：创建、修改、删除、试运行、发布、停用和复制操作的审计摘要。审计不保存 Secret、完整原始请求或完整规则响应。

### 6.2 API

- `GET /api/v1/incident-rules`：分页和状态筛选；
- `POST /api/v1/incident-rules`：创建草稿；
- `GET /api/v1/incident-rules/{id}`：读取详情；
- `PATCH /api/v1/incident-rules/{id}`：按期望版本修改草稿；
- `DELETE /api/v1/incident-rules/{id}`：只删除草稿；
- `POST /api/v1/incident-rules/{id}/dry-runs`：真实历史试运行；
- `POST /api/v1/incident-rules/{id}/publish`：发布通过试运行的当前版本；
- `POST /api/v1/incident-rules/{id}/disable`：停用已发布规则；
- `POST /api/v1/incident-rules/{id}/copies`：复制为独立草稿。

写操作在 MySQL 单事务完成。规则名称在未删除记录中唯一；请求字段有长度和数量限制；不存在、非法状态、版本冲突和校验失败返回明确错误码与中文安全提示。

## 7. 前端结构

前端增加独立 `IncidentRuleCenter` 和 `IncidentRuleWizard`，不把规则逻辑塞入 `App.vue`。API 适配、表单状态、规则摘要展示和试运行结果分别保持单一职责。

视觉保持现有深色石墨控制台、蓝色主操作和 14–16px 正文。向导桌面端使用左侧步骤、中央表单、右侧摘要；较窄窗口时摘要下移，步骤改为顶部横向，不出现横向滚动。核心输入、返回、草稿保存、试运行、发布和列表操作都必须可交互。

## 8. 失败与退化

- 规则列表读取失败：保留页面骨架并允许重试；
- 草稿保存失败：保留本地输入，禁止误报成功；
- 版本冲突：提示规则已被更新，允许重新加载，不自动覆盖；
- 试运行失败：草稿仍可编辑，发布保持禁用；
- 试运行结果截断：明确提示缩小范围或收紧规则，禁止发布；
- 数据库不可用：不影响现有告警接入和告警列表的领域语义，接口返回安全错误；
- 已发布规则当前不会自动生成 Incident，页面必须明确写明这是下一阶段能力。

## 9. 测试策略

- 领域单元测试覆盖校验、状态转换、版本冲突、中文摘要和窗口匹配；
- 持久化集成测试覆盖迁移、唯一约束、分页、事务回滚和审计；
- API 测试覆盖完整创建流程、非法输入、并发冲突、截断与状态权限；
- 历史试运行测试使用真实 Alert 仓储，覆盖来源/服务过滤、缺失 service、滚动窗口、AND 条件和重复命中合并；
- 前端测试覆盖空状态、四步导航、草稿恢复、字段错误、真实试运行结果、发布禁用条件和状态操作；
- 浏览器验证覆盖创建草稿到发布的主流程，并将选定设计图与同视口实现截图进行设计 QA。

## 10. 后续独立设计

下一阶段单独设计“候选 Incident 生成引擎”，明确发布规则的实时触发、候选去重、观察/确认/误报状态和 Alert 成员快照。该阶段通过后，才让 `PUBLISHED` 规则真正创建候选 Incident；再往后才进入自动取证和 AI 分析。
