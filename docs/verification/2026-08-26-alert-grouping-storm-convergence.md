# 告警分组与风暴收敛验收证据

## 验收结论

2026-08-26 完成。告警进入平台后先形成可解释的 AlertGroup，再以告警组为单位收敛事故关联任务；每条 SignalEvent、Alert 和最终 Alert-Incident 关系继续独立保留。告警中心和事故详情均已切换为组优先展示，原始告警仍可分页审计。

## 101 条真实风暴场景

使用本地 MySQL 8.4 中既有的真实 Alertmanager 压测数据验收：

- 同一生产服务、同一错误率症状在一分钟内产生 101 条不同 Alert；
- 后端形成 1 个 `STORM` 告警组，显示 101 条原始告警和 101 个影响资源；
- 告警组关联到 1 个 Incident，事故队列显示关联 101 条告警；
- 告警组详情第一页显示 1–100 条，第二页显示第 101–101 条；
- 事故详情优先显示 1 个关联问题组，再保留前 100 条原始告警兼容明细；
- 从告警组进入当前已打开的同一事故会重新读取后端事实，不再保留后台回填过程中的旧计数；
- 浏览器控制台没有错误或警告，页面没有展示 Token、来源 URI 或故障实验身份。

## 1,000 条并发容量

新增真实 MySQL 集成测试 `backend/tests/integration/test_alert_storm_convergence.py`：

- 10 个并发批次，每批 100 条，共接收 1,000 条不同告警；
- 精确重放首批 100 条不增加 SignalEvent、Alert、成员或任务；
- 最终数据库保留 1,000 条 SignalEvent、1,000 条 Alert、1,000 条 AlertGroupMember 和 1,000 条 IncidentAlertLink；
- 只形成 1 个 AlertGroup、1 个 Incident，组状态为 `STORM`，活动组关联任务为 0；
- 容量基线首次运行超过 187 秒仍未完成，定位到组刷新逐成员查询；改为一次聚合查询加一次代表告警查询后，用例 26.00 秒完成；
- 新增查询上限回归测试，成员数增长不会使单次组刷新查询数量线性增长。

## 安全与恢复

- 单批超过 100 条保持整批拒绝；发送方使用不超过 100 条的批次；
- 归组和组关联任务支持租约过期接管、最多五次尝试、固定错误码和人工重试；
- 历史回填稳定排序、分批执行且支持重放和并发收敛；
- 告警组读取失败不会回退演示数据，也不会阻断原始告警读取和人工事故处置；
- 新增 API 和页面只使用白名单摘要，不返回 Secret、原始 Webhook、无界标签或禁止实验身份。

## 已知边界

- 告警组首版只使用确定性高可信规则，不提供人工合并拆分或学习型归组；
- 事故详情的原始 Alert 兼容表仍最多返回前 100 条，完整成员通过告警组成员 API 独立分页；
- 告警确认、静默、通知升级、自动取证和 AI 分析不属于本规格；
- 本地 Vite 代理用于验收，不等同于生产身份控制器。
