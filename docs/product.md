# 产品定义

## 产品目标

构建通用型、AI 驱动的生产事故智能平台。平台从多种监控、异常捕获、变更和人工来源接收运行事件，将事件标准化为信号，经过去重、影响判断和可解释关联形成事故，再自动关联 Metrics、Logs、Traces、Kubernetes 和服务拓扑，生成可追溯的根因候选、因果链、处置建议和人工验证步骤。

## 核心闭环

多源事件 → SignalEvent → Alert → 可解释关联 → Incident → 通用诊断与专用增强 → 证据快照 → AI 分析 → 人工处置 → 恢复验证 → 复盘。

## 产品原则

- 信号不等于告警，告警不等于事故。
- Prometheus/Alertmanager 只是输入源之一，不决定事故边界。
- 完整遥测继续存放在原监控平台；本项目只保存有界摘要、事实和引用。
- 首版使用规则优先、可解释的事故关联，宁可少合并，不可误合并。
- AI 不决定执行任意查询，不直接访问监控、Kubernetes 或事故数据库。
- 未匹配专用增强包时仍执行通用诊断，并明确标记覆盖有限。
- 告警恢复不等于事故关闭；诊断失败不阻断事故运营。
- 生产诊断链路永远不知道故障实验身份、注入动作和标准答案。
- 首份可信报告目标为事故创建后 3 分钟内生成；这是阶段验收目标，不是当前已实现 SLA。

## 首批输入

- Alertmanager v4 Webhook Adapter；
- 受认证 CloudEvents HTTP Adapter；
- 授权人工事故报告入口。

Kubernetes Event、APM/Sentry、云监控、SLO、日志告警和 CI/CD 变更适配器属于后续能力。

## 用户价值

操作员面对的是一个事故，而不是散落在不同工具中的多条告警。事故页面应直接回答：

1. 哪些用户和业务受到影响；
2. 事故是否仍在持续，谁在负责；
3. 系统认为发生了什么；
4. 哪些事实支持或反驳根因候选；
5. 还缺少哪些证据；
6. 当前建议采取什么动作；
7. 服务是否已经真正恢复。

## 非目标

- 故障注入、实验场景、Chaos 控制和实验恢复；
- 自动修复和任意命令执行；
- AI 自主生成 PromQL、日志、Trace 或 Kubernetes 查询；
- 替代 Prometheus、日志平台、APM 或 OpenTelemetry Collector；
- 首版黑盒机器学习自动事故关联；
- 首版完整值班排班、电话通知和外部工单平台。
