# 正式 Incident 取证与受控 Dify 诊断迁移

## 状态

已确认

## 背景与目标

告警生命周期和规则评估已经以 `alert_lifecycles`、`operational_incidents` 为当前正式模型运行。现有取证和 DiagnosisRun 仍引用历史 `incidents`、`incident_evidence_runs`，使新产生的正式 Incident 无法自动取证或启动 Dify 诊断。

本规格将取证、诊断快照、诊断任务和可信报告完整迁移到正式 Incident 模型。`operational_incidents` 是新运行的唯一事故事实来源；Dify 保持为平台主控下的无状态受控执行器。

## 范围

- 为正式 Incident 建立唯一自动取证运行、不可变证据项与持久化任务；
- 为正式 Incident 建立 DiagnosisRun、输入快照、工具回执、报告和持久化任务；
- 将 Incident 详情的“监控取证”和“智能分析”入口切换到正式模型；
- 复用既有版本化只读取证包、Dify 调用适配器、能力令牌和报告校验语义；
- 以 `INC-20260916-001` 验证新 Incident 的取证和真实 Dify 主流程。

## 非目标

- 不向旧 `incidents`、旧 EvidenceRun 或旧 DiagnosisRun 双写、镜像或同步；
- 不迁移、修复或删除旧历史数据；
- 不扩大 Dify 的网络、工具、查询或写入权限；
- 不在本次实现证据详情工具的编排、知识检索、RAG 或自动修复；
- 不改变 Alertmanager / CloudEvents 的接收协议、Alert 生命周期或 Incident 规则语义。

## 设计

### 领域与持久化边界

新增正式模型专属的取证、诊断运行、快照、任务、回执与报告记录；每条记录只持有 `operational_incident_id`。新表名称以 `operational_` 前缀区分，禁止新运行访问历史事故表。

同一正式 Incident 最多存在一个自动取证运行和一个活动诊断运行。唯一约束、事务重试、持久化租约和幂等操作记录共同保证并发收敛。旧表只允许历史只读 API 或迁移工具使用，不再被 Worker 写入。

### 自动取证

正式 Incident 首次创建的同一事务内写入唯一自动取证运行和待处理任务。Worker 根据 Incident 的环境、服务、关联 Alert 生命周期和固定时间锚点执行既有 Prometheus、Elasticsearch、SkyWalking 版本化只读取证包。各来源可独立失败；成功、部分成功、失败的语义与现有 EvidenceRun 保持一致。

### 人工诊断与 Dify

操作员只能选择同一正式 Incident 下已成功或部分成功的取证运行创建诊断。创建事务冻结：Incident 安全投影、关联 Alert 生命周期安全字段、最多 100 条证据项内容指纹、环境与服务范围。平台签发单次、5 分钟有效的只读能力令牌。

真实 Dify Worker 固定调用已发布的 `incident-diagnosis.v1` Workflow，只传递诊断运行 ID、能力令牌和输出契约版本。Workflow 只能读取该运行的冻结快照；不得连接数据库、监控、Kubernetes、飞书、任意 URL 或写入接口。平台校验结构化输出与快照引用后，才将报告置为 `REPORT_READY`；否则进入 `REVIEW_REQUIRED` 或 `FAILED`。

### API 与页面

正式 Incident API 在既有 `/api/v1/incidents/{incident_id}` 资源下提供取证运行与诊断运行的创建、列表和详情。前端仅显示当前正式模型的取证历史、诊断状态、可信报告和人工建议；不展示能力令牌、模型思维过程、原始 Webhook、未脱敏日志或 Dify 密钥。

### 迁移顺序

1. 先建立新模型、迁移和仓储，并以失败测试覆盖唯一边界、状态机、快照范围与旧表隔离；
2. 接入自动取证任务和正式 Incident 详情取证读取；
3. 接入正式 DiagnosisRun、受限快照工具、Dify Worker 与报告校验；
4. 切换前端入口并完成真实 Incident 沙箱验证；
5. 更新当前状态，明确旧模型仅历史保留。

## 安全与恢复

- Dify API Key、能力令牌和监控凭据只从运行环境读取，不写入数据库正文、日志、API、前端或快照；
- 能力令牌按运行和到期时间严格校验，拒绝跨 Incident、跨运行、过期和扩权请求，并写入有界工具回执；
- Dify、模型、监控源或 Worker 的失败不得阻断 Alert 接收、Incident 规则评估、人工确认/解决或飞书通知；
- 新旧数据表没有运行时同步，失败可安全停留在旧链路历史可读、新链路不发布报告的状态；
- 所有任务采用租约、有限重试与稳定错误码，进程重启后可回收。

## 验收条件

- 新产生的 `operational_incidents` 不写入旧 `incidents`，且自动创建唯一正式取证任务；
- 新取证运行仅引用正式 Incident 与关联 Alert 生命周期，三类来源的成功、部分成功和失败安全退化可验证；
- 同一正式 Incident 的并发取证和诊断请求收敛，幂等重放不重复外部调用；
- 诊断快照不包含 Secret、实验身份、原始 Webhook、任意查询文本或模型思维过程；
- Dify 只能通过短期能力令牌读取同一正式 DiagnosisRun 的快照，跨运行和过期令牌被拒绝；
- 无效模型输出、无效引用、超长输出或未标记假设不能成为可信报告；
- `INC-20260916-001` 能完成：正式 Incident → 取证 → 手动启动诊断 → Dify 草案 → 平台校验的沙箱主流程；
- 后端统一测试、静态检查、迁移升降级、前端测试和生产构建全部通过。
