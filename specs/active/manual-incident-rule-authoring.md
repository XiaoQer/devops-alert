# 手动 Incident 规则配置

## 状态

设计已完成，等待用户确认书面规格后实施。

## 背景与目标

平台已经能够把外部通知投影为准确的 Alert 生命周期，但尚未定义如何从 Alert 识别 Incident。第一阶段先提供完全由用户手动配置的 Incident 规则，不内置任何规则，也不恢复旧的事故关联逻辑。

本阶段交付一个真实可用的规则管理闭环：创建草稿、配置匹配范围和触发条件、用历史 Alert 试运行、发布或停用规则。完整设计见 `docs/superpowers/specs/2026-08-31-manual-incident-rule-authoring-design.md`。

## 范围

- Incident 规则列表、空状态和状态筛选；
- 四步创建流程：基本信息、匹配范围、触发条件、试运行与发布；
- 草稿保存、编辑、复制、发布和停用；
- 基于真实历史 Alert 的只读试运行；
- 结构化条件、中文规则摘要和字段级校验；
- MySQL 持久化、乐观并发、分页和有界查询；
- 规则管理审计，不记录 Secret 或完整原始请求。

## 非目标

- 内置规则或规则模板；
- 发布后自动创建 Incident 或候选 Incident；
- Incident 列表、确认、误报、合并、关闭等运营流程；
- 拓扑、文本相似度、自动取证、AI 分析或自动修复；
- 任意表达式、脚本、正则或原始 JSON 规则编辑器。

## 验收条件

- 首次进入 Incident 规则页时，真实展示空状态，不生成演示规则；
- 用户可完成四步流程并保存草稿，刷新页面后内容仍存在；
- 环境是必选隔离边界，来源和服务是可选过滤条件；
- 聚合方式只允许“同一服务”或“同一实体”；
- 观察窗口只允许 1 至 60 分钟；
- 第一版条件只支持“不同 Alertname 数量”“活动告警数量”“不同实体数量”“最高级别至少为”，且所有条件使用 AND；
- 同一条件类型不可重复，至少配置一个计数条件；
- 试运行读取用户选择的最近 1、6、12、24 或 48 小时真实 Alert，返回命中的时间窗口、分组、数量和示例告警，不写入 Incident；
- 试运行查询最多扫描 10,000 条 Alert，返回最多 100 个命中结果，并明确提示截断；
- 未成功试运行的草稿不能发布；规则修改后旧试运行结果失效；
- 发布后的规则不可直接修改；可复制为新草稿或停用；
- API 使用版本号防止两个页面互相覆盖；
- 后端统一验证、前端测试和生产构建全部通过；
- 页面忠实采用用户选择的第 1 个分步向导方案，正文密度和现有告警中心一致。
