# 服务目录与可解释事故关联

## 状态

已确认，待实施。

## 背景与目标

多源接入已经能够把人工报告、Alertmanager 和 CloudEvents 转换为 SignalEvent 与 Alert，但外部 Alert 尚不会形成 Incident。本规格增加轻量服务目录、持久关联任务和规则优先的可解释事故关联，使满足运营门槛的生产告警可靠创建或加入 Incident。

## 范围

- `service + environment` 唯一的版本化服务目录；
- 同环境一跳依赖和依赖环拒绝；
- Alert 有效变化时同事务产生持久关联任务；
- MySQL 租约、过期接管、有界重试和人工重试；
- critical/high、ACTIVE、production、服务已启用的固定进入门槛；
- 同服务 15 分钟唯一候选自动关联；
- 多候选歧义和一跳同症状只提示、不自动合并；
- Incident 创建、Alert 关系和不可变关联决策；
- 固定原因码、有界事实和中文解释；
- 服务目录管理、关联结果读取和失败任务重试 API。

## 非目标

- 自动取证、DiagnosisRun 自动创建、Worker 或 AI；
- 标题相似度、向量检索、LLM 或机器学习关联；
- 人工合并拆分、事故状态写接口和恢复闭环；
- 维护窗口、变更事件、多跳拓扑和自动服务发现；
- 目录变化后自动批量重算历史 Alert；
- 前端和生产部署制品。

## 设计

完整设计见 `docs/superpowers/specs/2026-08-25-service-catalog-correlation-design.md`。

核心链路：

`Alert 投影变化 → correlation_jobs → 确定性门槛与候选规则 → Incident + incident_alert_links + correlation_decisions`

关联任务与 Alert 变化同事务写入，关联处理异步执行。关联失败不得回滚或阻断已接收的 SignalEvent 和 Alert。告警恢复只形成关联决策，不自动关闭 Incident。

## 安全与恢复

- 管理接口只接受 `II_API_TOKEN`；其他来源 Token 不可交叉使用；
- 服务目录采用乐观锁，不物理删除历史服务和依赖；
- 关联任务使用租约、过期接管、最多五次重试和固定错误码；
- 关联动作在单事务内创建 Incident、关系与决策，失败零残留；
- 决策只保存固定规则、原因、白名单事实和候选 ID；
- Secret、原始来源 URI、查询、完整标签、异常正文和禁止实验身份不得进入任务、决策、审计或 API 响应；
- 关联不可用不影响健康检查、外部告警接入和人工事故处置。

## 验收条件

- 服务目录唯一、版本更新、停用和有界分页行为可验证；
- 自依赖、跨环境、重复依赖和依赖环均被拒绝；
- 不符合 ACTIVE、critical/high、production、目录启用任一条件的 Alert 不创建 Incident，并有中文原因；
- 同服务窗口内零、一个、多个候选分别创建、自动关联和歧义创建独立事故；
- 一跳同症状只记录可能相关，不自动合并；
- 跨环境、窗口外和终态 Incident 不参与候选；
- 重放、迟到和孤立恢复不产生重复任务；
- 任务租约、过期接管、失败重试、人工重试和旧版本跳过可验证；
- 同服务并发处理不会产生错误重复关联，一个 Alert 最多属于一个 Incident；
- Alert 恢复不改变 Incident 状态；
- 外部 Alert 创建 Incident 后 DiagnosisRun 数量保持不变；
- 每个关联或拒绝结果都有规则版本、固定原因码、有界事实和中文解释；
- 统一静态检查、类型检查、迁移、MySQL 集成测试和覆盖率门槛全部通过。

## 验证证据

尚未实施，不得把服务目录、自动事故创建或关联标记为可用。
